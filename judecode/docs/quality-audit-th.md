# ตรวจคุณภาพงานโค้ดและเรื่องเล่า — 15 ตุลาคม 2026

ตรวจจาก source ของ Jude Code และ regression tests ในเครื่อง ไม่ได้ประเมินวิดีโอจริงหรือ benchmark งานใหญ่ด้วยโมเดลจริงในรอบนี้

## สิ่งที่ขาด

| ส่วน | หลักฐานในระบบ | ผลต่อผลงาน |
|---|---|---|
| ความครบของโค้ด | project.py ตรวจเฉพาะ features/checks ที่โมเดลลงทะเบียน | ถ้าลืม requirement ตั้งแต่ต้น ทุก check อาจผ่านแต่งานไม่ครบ |
| คุณภาพการทดสอบ | เดิมถือ exit code 0 เป็นหลัก | unittest discover ที่เจอ 0 tests ก็เคยถือว่าผ่านได้ |
| โครงเรื่อง | director_plan เดิมเก็บ prompt, narration, duration และ continuity | ไม่มีช่องให้ระบุเหตุการณ์ที่เปลี่ยนสถานการณ์ มุมกล้อง และสภาพท้ายฉากอย่างชัดเจน |
| จังหวะคลิป | render ใช้ max(duration, audio_duration) | เสียงยาวทำให้ค้างเฟรมท้าย ความยาวหนังเพิ่มแต่การเคลื่อนไหวไม่เพิ่ม |
| เสียงและการตัดต่อ | director ปิด generate_audio และประกอบ narration ตามฉาก | ไม่มีชั้น ambience/เอฟเฟกต์/ดนตรีและการลดเสียงอัตโนมัติใน workflow นี้ |
| การตรวจผลงาน | status completed หลังประกอบ MP4 | บอกว่าเรนเดอร์เสร็จ ไม่ได้พิสูจน์ความสนุก ความต่อเนื่องหรือความชัดของเสียง |

## การแก้ในรอบนี้

- เพิ่มแนวทาง coding ให้แปลงคำขอเป็นเส้นทางใช้งานที่สังเกตผลได้ ทำ UI/API/storage ให้จบหนึ่งเส้นทางก่อนขยาย และย้อนตรวจ requirement ที่ตกหล่นก่อนส่งมอบ เป็นคำแนะนำโมเดล ไม่ใช่การพิสูจน์ coverage อัตโนมัติ
- ไม่ยอมรับ runner summaries ที่ระบุรัน 0 tests เป็น acceptance success แม้ exit code 0; เก็บ exit code เดิมและ validation_error ให้ตรวจย้อนหลังได้ กฎนี้ตรวจรูปแบบ summary ที่รู้จัก ไม่ใช่การตรวจความถูกต้องของ tests ทุกชนิด
- เพิ่ม beat, camera, end_state ในแผนฉาก เก็บข้าม restart และส่งถึง prompt สร้างภาพ/วิดีโอ แผนเก่ายังใช้ได้และมีคำเตือนหากไม่มีข้อมูล
- director_status คืน quality.status=unreviewed เสมอ เพราะไม่มีระบบตรวจภาพ/เสียงจริง และแจ้ง missing_direction/narration_overrun โดยไม่คิดเงิน
- บันทึก planned_seconds/rendered_seconds/extended_hold_seconds หลัง render; ค่านี้เทียบเสียงกับระยะฉากที่วางไว้ ไม่ใช่การวัด motion หรือระยะ source video จริง ยังคงไม่ตัดบทพูดและไม่สร้างงานเสียเงินซ้ำเอง

## วิธีทำงานให้ได้ผลดีกว่าเดิม

งานโค้ด: เริ่มจากตัวอย่างใช้งานและผลที่ต้องเห็น เช่น ขายสินค้า → ยอดสต๊อกลด → reload แล้วยังถูกต้อง → ยกเลิกแล้วคืนสต๊อก → ผู้ไม่มีสิทธิ์ทำไม่ได้ ตรวจผ่าน UI/API จริง และแยกสิ่งที่ยังไม่ทดสอบออกจากสิ่งที่ผ่านแล้ว อย่าใช้ build ผ่านเป็นหลักฐานแทน behavior

งานเรื่องเล่า: กำหนดคนดูและอารมณ์ปลายทาง → เปิดด้วยคำถามหรือเหตุการณ์ → ตัวละครมีเป้าหมายและอุปสรรค → ต้องตัดสินใจ → จบด้วยผลที่ตอบสิ่งที่เปิดไว้ แต่ละฉากควรเปลี่ยนสถานการณ์ ใช้มุมภาพเพื่อแสดงอารมณ์ ไม่ใช่เปลี่ยนมุมเพราะต้องให้หลากหลาย และเว้นจังหวะให้ภาพเล่าเอง

ตัวอย่างแมวกลับบ้าน: แมวเห็นไฟบ้านดับกลางฝน → ทางกลับถูกน้ำตัด → มันเลือกช่วยลูกแมวแทนรีบกลับ → กลับถึงบ้านพร้อมเพื่อนใหม่ เหตุการณ์เชื่อมกันด้วยการตัดสินใจ ไม่ใช่เพียงภาพแมวเดินหลายสถานที่

## งานต่อที่ควรวัดก่อนอ้างว่าคุณภาพดีขึ้น

1. ใช้โจทย์โค้ดจริงหนึ่งงานที่มี acceptance scenarios กำหนดจากคำขอไว้ก่อน ให้ระบบทำจนจบแล้วทดสอบซ้ำอย่างอิสระ บันทึกสิ่งที่ขาด จำนวนรอบแก้ เวลา และค่าใช้จ่าย
2. ทำคลิปเรื่องเดียวกันสองเวอร์ชันและดู/ฟังจริง เปรียบเทียบความเข้าใจเรื่อง อารมณ์ จังหวะ ความต่อเนื่อง เสียง และภาพค้าง ไม่ใช้คะแนนที่โมเดลให้ตัวเองเป็นข้อยืนยัน
3. เพิ่ม workflow แก้เฉพาะฉาก/บทพูดพร้อม invalidation ของ render ที่เกี่ยวข้องและการรักษา paid receipts; จากนั้นเพิ่มการจัดระยะภาพตามเสียงโดยไม่ค้างเฟรมยาว
4. เพิ่ม sound design, ducking, ซับไทย และการตรวจภาพ/เสียงเมื่อมีเครื่องมือรองรับ เลือกทำตามโจทย์จริง ไม่ถือว่าทุกเรื่องต้องมีเพลงหรือเอฟเฟกต์

รอบนี้แก้ source ใน Mac workspace; ต้อง restart process เพื่อโหลด ยังไม่ได้ deploy Ubuntu หรือ rebuild แอป และยังไม่ได้ใช้ paid media generation เพื่อประเมินผล
