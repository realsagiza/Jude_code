# Qwen + ผู้ช่วย GLM

โมเดลหลักเดิมยังรับทุกคำขอใหม่ก่อน (เครื่องนี้ใช้ qwen/qwen3.7-flash)
เมื่อประเมินว่าโจทย์โค้ดยาก เช่น วิเคราะห์บั๊กหลายไฟล์ เปลี่ยนโครงสร้างใหญ่
หรือแก้ซ้ำไม่คืบหน้า จะเรียก `expert_help` พร้อมเหตุผล เป้าหมาย ข้อจำกัด
และวิธีตรวจว่างานเสร็จ แล้ว GLM รับช่วงวงจรเครื่องมือเดิมแบบลำดับเดียว
ไม่มี agent ขนานและไม่มีการคัดลอกไฟล์ไป workspace ใหม่

GLM เห็นประวัติที่ผ่านระบบจัดการ context เดิม อ่าน/แก้ไฟล์และรัน shell ได้
ผ่าน permission, backup, sandbox และ verification เดิม การมี tool ไม่ได้ข้ามสิทธิ์
เมื่อเรียก `expert_return` หรือให้คำตอบสุดท้ายโดยไม่เรียก tool จะกลับให้โมเดลหลักสรุป
คำตอบของผู้ช่วยไม่ใช่หลักฐานว่า tests ผ่าน ต้องตรวจผลจริง

## ตั้งค่าใน judecode/.env แล้ว restart

```
JUDECODE_EXPERT_ENABLED=1
JUDECODE_EXPERT_MODEL=z-ai/glm-5.3
JUDECODE_EXPERT_MAX_TURNS=24
JUDECODE_EXPERT_MAX_HANDOFFS=2
JUDECODE_EXPERT_MAX_TOKENS=16384
```

ใช้ OpenRouter key และ endpoint เดิม ไม่ต้องเพิ่ม key และไม่เปลี่ยนโมเดลหลัก
ค่าเหล่านี้เป็น defaults อยู่แล้ว ปิดด้วย JUDECODE_EXPERT_ENABLED=0
ใช้ได้เมื่อมี OpenRouter key เท่านั้น ไม่มีการสลับ provider อื่นเมื่อ GLM ล้มเหลว

- จำกัดรวม 24 expert requests ต่อคำขอผู้ใช้ ไม่รีเซ็ตเมื่อส่งต่อรอบสอง
- จำกัดส่งต่อ 2 ครั้งต่อคำขอ ป้องกันวนสลับโมเดล
- max_tokens จำกัดต่อคำตอบ ไม่ใช่งบเงิน; reasoning และบริบทส่งซ้ำมีค่าใช้จ่าย
- ตัวเลขเงินใน budget tracker เดิมยังเป็น estimate ไม่ใช่ราคา/usage จริงของ GLM
  ขีดจำกัดรอบและ tokens ไม่รับประกันยอดเงินสูงสุด
- Ctrl+C หยุดตามกลไกเดิม; /continue เก็บโมเดลผู้ช่วยและจำนวนรอบเดิม
- /resume เก็บ routing ใน transcript; คำสั่งผู้ใช้ใหม่เริ่มที่โมเดลหลักและรีเซ็ตโควตา
- การจัดว่าโจทย์ยากเป็นการตัดสินของโมเดลตาม prompt ไม่ใช่ classifier ที่รับประกัน
- scheduler และ sandbox ยังมี allowlist เดิม จึงอาจปฏิเสธ expert_help
- เมื่อถึงขีดจำกัดหรือ API ล้มเหลว จะหยุดและรายงานข้อจำกัด ไม่รับประกันทุกงานเสร็จ

ทดสอบด้วย fake providers และ real engine ไม่ได้ยืนยันคุณภาพ GLM บนงานจริง
